# 自ら判断して動くロボットを作るまで

[READMEに戻る](../../README.ja.md) | [한국어](../ko/project-story.md)

## テーマを決めるまで

このプロジェクトは、IoT（モノのインターネット）の授業で課題の代わりとなるプロジェクトとして始まった。最初からロボットを作ると決めていたわけではない。視覚障害者向けの杖、アルコール検知器、人を自動検知するWebアプリなど、複数のテーマを検討した。

その中で、Raspberry PiとLLM APIをつないだらどうだろうかと考えた。あらかじめ決められたボタンを押すだけの車ではなく、人が話した言葉を聞き、状況を見て、次の行動を選ぶロボット。「自ら考え、判断し、動く」という構想が、ほかの候補よりも強く心を引いた。

## 実際につないだ処理の流れ

最終統合版の流れは次のとおりである。

1. USBマイクでウェイクワードと韓国語のコマンドを聞き取る。
2. Geminiがコマンドを許可された動作のJSONシーケンスに変換する。
3. プログラムが動作名と繰り返し回数を検査する。
4. OpenCVカメラ、HC-SR04距離センサー、GPIOモーターを必要な順序で使用する。
5. 結果や質問をgTTSで発話する。

カメラを使った質問と物体への接近にはGemini Visionを使用した。新たにシーンを撮影してAPIへ送る必要があるため、入力から動作までには時間がかかった。映像にはロボットが止まって考えているように見える場面があるが、実際には撮影、アップロード、推論、応答を待っている時間である。

## コードより難しかった実機

プログラムにエラーがなくても、実機がそのまま動くとは限らなかった。バッテリーの電圧が下がるとモーターの力と回転量が変わり、配線、USBデバイス番号、床の摩擦、センサーの向きなど、コード外の変数が次々に生じた。

技術的な問題とは別に、「本当に完成するのだろうか」という不安も大きかった。プロジェクトの規模は明らかに大きく、どこか一つでも失敗すればデモ全体が止まってしまう。そのため、配線、モーター、距離、カメラ、音声を一度につなぐのではなく、一層ずつ確認していく方法が重要だった。

## 安全条件

前進直前には超音波で距離を再測定し、デフォルトでは25 cm以下なら前進をブロックした。「障害物まで移動」では走行中も繰り返し距離を確認し、デフォルトでは障害物の18 cm手前で停止するようにした。この条件はモデルに与えるプロンプトだけでなく、`hardware.py`の条件分岐にも実装している。

ただし、センサーは前方に一つしかなく、物理的な緊急停止ボタンがコードに含まれているわけでもない。そのため、この実装を完全な自動運転や完全な衝突防止とは説明していない。

## 授業での発表

7月9日の授業で実機ロボットを発表した。原理をすでに理解していた制作者とは異なり、見る人にとっては、音声コマンドを聞いたロボットがカメラで確認して動く場面が最初に目に入った。その反応は、AIが初めて製品デモとして登場したときのように、内部構造よりも目の前で起こる動作そのものに関心が集まる雰囲気だった。

## 映像と公開コードが異なって見えた理由

最初にリポジトリを公開した際、最終統合版ではなく、簡略化された実験コードを公開してしまった。その公開版には出力用の移動スタブだけが残り、カメラ、センサー、GPIOはメインの実行経路に接続されていなかった。その後、文書を整理した時点では公開コードだけを根拠としていたため、「映像の機能は現在のコードでは再現できない」と正確に記載した。

2026年8月9日、5月28日に保存した最終発表版の`robot_pj_long_listen`を改めて照合した。このバックアップでは、映像で使用したGPIOモーター、超音波センサー、カメラ、Gemini Vision、マイクによる音声認識、TTSの流れがすべて接続されていた。そこで、次の原則に従ってリポジトリを復元した。

- 最終発表版のPythonの動作を基準とする。
- 失効済みのAPIキーが含まれていた過去のバックアップは使用しない。
- キーは`.env`と環境変数からのみ入力する。
- 映像で実際に行った機能と、現在のコードの制限事項をあわせて記録する。
- 7月9日の簡略版公開と8月9日の復元という事実を隠さない。

この過程で分かったのは、「公開されたリポジトリが、制作当時の全記録と同じとは限らない」ということだった。映像とコードが一致しないときに機能を推測して文書を書くのではなく、保管していた版の日付とファイル内容を確認し、その差異を記録する必要があった。

## 今後の改善点

現在の実装も完成形ではない。センサーのタイムアウトをより慎重に処理し、後方と側面のセンサーや物理的な緊急停止を追加して、Gemini Visionの遅延を減らす作業が残っている。ハードウェアがない環境でも安全条件を繰り返し検証できるよう、仮想デバイス層と単体テストも強化する必要がある。
